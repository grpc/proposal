## Abstract

This proposal adds a new experimental C-core call credentials API for DPoP
(Demonstration of Proof-of-Possession, RFC 9449). The API allows a caller to
provide an OAuth2 access token and an EC P-256 private key. For each RPC, gRPC
will generate a DPoP proof and attach it to the request metadata.

Unlike a basic DPoP implementation, this proposal also binds the proof to the
current TLS session by incorporating per-connection TLS channel binding
material. The additional TLS binding prevents a captured DPoP proof from being 
replayed successfully on a different TLS connection when the verifier enforces the binding.

## Background

DPoP is a sender-constrained token mechanism defined in RFC 9449. A client
proves possession of a private key by signing a JWT and sending it alongside an
access token. The server can then verify that the caller possessed the private
key corresponding to the public key embedded in the proof.

In standard DPoP, the access token is bound to the proof-of-possession key, but
not to a specific transport connection. If both the access token and the
private key are exfiltrated from the client, they can still be replayed from a
different endpoint. For environments that already rely on transport security,
binding the proof to a specific TLS session provides an additional defense
layer.

The motivating use case for this proposal is gRPC C-core clients that need a
public API for sender-constrained bearer tokens and want stronger replay
protection than bearer tokens or key-bound DPoP alone can provide.

## Proposal

This proposal introduces a new experimental public C-core API:

```c
GRPCAPI grpc_call_credentials* grpc_dpop_credentials_create(
    const char* access_token, const char* ec_private_pem, void* reserved);
```

The parameters are:

*   `access_token`: the raw OAuth2 access token, without any scheme prefix.
*   `ec_private_pem`: a PEM-encoded EC private key for the P-256 curve. The
    proof is signed with ES256.
*   `reserved`: reserved for future use and must be `nullptr`.

When these credentials are attached to a call, gRPC C-core will:

1.  Require a TLS-secured transport.
2.  Require TLS channel binding material for the current connection.
3.  Construct the DPoP `htu` from the request URI authority and path.
4.  Generate a DPoP proof JWT for the RPC.
5.  Attach the following metadata:
    *   `authorization: DPoP <access_token>`
    *   `dpop: <proof-jwt>`

If any required precondition is not met, metadata generation fails closed and
the RPC is not sent with partial or downgraded credentials.

### Proof Contents

Each DPoP proof generated by gRPC will include the usual DPoP fields:

*   `typ: dpop+jwt`
*   `alg: ES256`
*   embedded public JWK for the EC P-256 key
*   `htm`
*   `htu`
*   `ath`
*   `jti`
*   `iat`

In addition, the proof will contain a `tls_channel_binding` claim whose value
is derived from the current TLS session. This claim is the core semantic change
proposed here.

### TLS Channel Binding

This proposal introduces a new auth context property:

```c
#define GRPC_TLS_CHANNEL_BINDING_PROPERTY_NAME "tls_channel_binding"
```

The property value is a string of the form:

```text
<binding-type>:<base64url(binding-bytes)>
```

The binding is computed from the active TLS session as follows:

*   On TLS 1.3, gRPC uses the RFC 9266 `tls-exporter` channel binding.
*   On TLS 1.2, gRPC prefers RFC 5929 `tls-unique` when available.
*   If `tls-unique` is unavailable, gRPC falls back to `tls-exporter`.

This property is populated by the TLS transport security stack and exposed via
the auth context so that call credentials can bind generated proofs to the
connection actually carrying the RPC.

### Failure Behavior

The credentials object will reject metadata generation in the following cases:

*   the transport is not TLS-secured
*   the auth context indicates a non-SSL transport security type
*   TLS channel binding material is unavailable
*   request authority or path is missing
*   the supplied private key cannot be parsed or cannot sign the proof

This proposal intentionally does not define a fallback mode that emits a
standard DPoP proof without TLS binding. Callers choosing this API are opting
into sender-constrained credentials that are bound to the connection, and the
library should preserve that invariant.

### Scope

This proposal adds a C-core public API and corresponding C-core implementation.
It does not require public API changes in wrapped languages as part of the
initial rollout, although wrapped runtimes may choose to expose this capability
later.

## Rationale

The design goal is not merely to support DPoP, but to support a stronger
sender-constrained token mechanism suitable for gRPC clients that already depend
on TLS.

The main alternatives considered were:

*   Implement standard DPoP without TLS session binding.
    This would still improve on bearer tokens, but it would not prevent replay
    when both the token and the DPoP private key are stolen from the client.

*   Introduce a more generic hard-bound credentials framework first.
    That would likely be reusable for other schemes, but it would significantly
    increase scope and delay a concrete API for the immediate DPoP use case.

*   Silently omit DPoP metadata when TLS channel binding is unavailable.
    This would create downgrade behavior that is hard for applications to
    detect. Failing closed is safer and makes misconfiguration visible.

*   Use only one channel binding mechanism.
    Restricting the design to only `tls-exporter` or only `tls-unique` would
    simplify the behavior, but it would either unnecessarily reduce coverage on
    supported deployments or fail to take advantage of the strongest available
    mechanism for a given TLS version.

This proposal chooses a narrow C-core API because the immediate need is a new
public credentials constructor. The transport-side channel binding property is
kept generic so it can be reused by future credential mechanisms if needed.

## Implementation

The initial implementation is under review in:

*   `grpc/grpc` PR [#43311](https://github.com/grpc/grpc/pull/43311)

That implementation adds:

*   the public C API `grpc_dpop_credentials_create()`
*   a new internal DPoP call credentials implementation
*   TLS channel binding extraction in the SSL/TSI transport stack
*   auth context plumbing for the `tls_channel_binding` property
*   unit tests covering successful proof generation and fail-closed behavior

The expected rollout order is:

1.  Land this gRFC in `grpc/proposal`.
2.  Update the implementation PR as needed based on gRFC review feedback.
3.  Merge the implementation in `grpc/grpc` after gRFC approval.

## Open issues

*   The `tls_channel_binding` claim is intentionally gRPC-specific and is not a
    standard DPoP claim defined by RFC 9449. Review should confirm that this is
    the right extension point versus expressing the binding by some other means.

*   This proposal does not define a server-side verification helper in gRPC.
    Verification is expected to be handled by the application or upstream
    service infrastructure. If that proves insufficient, a follow-up proposal
    may be needed.
    
### Verification Guidance (Informative)
Although gRPC does not ship server-side verification, implementers building
a verifier should, at minimum:
*   Recompute the expected `tls_channel_binding` value from their own TLS
    session and compare against the claim.
*   Verify the DPoP proof per RFC 9449 (signature, `htm`, `htu`, `iat`
    freshness, `jti` replay cache) before trusting the channel binding claim.
*   Reject requests where `tls_channel_binding` is present but the
    connection did not negotiate a TLS version/cipher suite that supports
    the claimed binding type.
This section is non-normative and intended to reduce the chance of
inconsistent verifier implementations across services.
